# Phase 2 — PostgreSQL Modeling, Prisma & Seed

Mirrors the structure of [docs/MIGRATION-PHASES.md](../MIGRATION-PHASES.md) (Fase 2) in
English. Builds on [phase-1-nextjs-foundation.md](./phase-1-nextjs-foundation.md).

## Objective

Stand up a relational schema in PostgreSQL, modeled with Prisma, and populate it via a seed
script equivalent to `src/domain/mock.ts` — **without connecting the application to it yet**.
The app keeps running against `src/domain/store.ts` and the mock; Phase 3 is the swap.

**Decisions applied:** D05 (independent entities), D06 (Prisma), D07 (Supabase), D08
(shared DB + `userId`), D10 (users table), D11 (UUIDs from the DB), D12 (native enums), D13
(date vs. timestamptz), D14 (`SessionAttempt` history table), D15 (session/attempt model),
D27 (schema for soft delete), D28 (seed from mock).

## Scope

- **Local + shared database**: `docker-compose.yml` runs Postgres 17 for day-to-day dev
  (host port `55432` to avoid clashing with other local Postgres containers); Supabase is
  the target for the shared/prod database. Both are reached purely through env vars
  (`DATABASE_URL` for the pooled/app connection, `DIRECT_URL` unpooled for migrations).
- **Prisma schema** (`prisma/schema.prisma`): `User`, `Book`, `Chapter`, `Question`,
  `RevisionSession`, `SessionAttempt` as independent, related models (D05).
  - UUID primary keys generated by the database (`gen_random_uuid()`, D11).
  - Native PostgreSQL enums for `ReadingStatus`, `ConsolidationState`, `SessionMode`,
    `Performance`, `Difficulty` (D12). `Importance` stays a plain `Int` (1–3); the UI already
    renders it as dots, not a label, so an enum adds no value.
  - `@db.Date` for calendar dates (`startDate`, `endDate`, `lastRevision`, `nextRevision`);
    `@db.Timestamptz(3)` for events (`createdAt`, `updatedAt`, `startedAt`, `completedAt`,
    `attemptedAt`) (D13).
  - `userId` on `Book` and `RevisionSession` (D08); `deletedAt` on `User` and `Book` (D27).
  - `@@unique([bookId, number])` on `Chapter`.
  - Cascades: `Book → Chapter → Question` cascade on delete; `RevisionSession →
SessionAttempt` cascades; `SessionAttempt.questionId` is nullable with `onDelete:
SetNull`, so physically deleting a question (allowed per D27) never destroys attempt
    history.
  - No `coverGradient` column — deferred: Phase 3 derives the fallback gradient
    deterministically from the book id at render time, reusing `COVER_GRADIENTS`.
    `coverUrl`/`googleBooksId` exist on `Book` for Phase 4 (D30) but stay unused this phase.
  - No `difficultTopics` column — dropped; `SessionAttempt` is the real source of truth for
    difficulty going forward (D14).
- **Migration**: `prisma migrate dev --name init`, committed under `prisma/migrations/`.
- **Seed** (`prisma/seed.ts`, run with `tsx`): idempotent (deletes in FK-safe order first).
  - One dev `User` (`name: "Rafael"`, from `PLACEHOLDER_USER`) with `email` from the required
    `SEED_USER_EMAIL` env var; `authUserId` stays `null` until Phase 4.
  - Each `MOCK_BOOKS` entry becomes a `Book` with nested `Chapter`s and `Question`s.
  - Each `RevisionRecord` becomes a `RevisionSession` (`startedAt`/`completedAt` set to the
    record's date at UTC midnight); `difficultTopics` is dropped.
  - Only the **latest** session per book gets synthesized `SessionAttempt` rows, built from
    questions carrying `lastPerformance` — that field has no history in the mock, so it can
    only stand in for the most recent attempt. Books with no revisions (`b5`, `b6`, `b7`) get
    no sessions or attempts.

## Deliverables

- `docker-compose.yml`, `.env.example`, `pnpm-workspace.yaml` (`onlyBuiltDependencies` for
  Prisma's postinstall scripts).
- `prisma/schema.prisma`, `prisma/migrations/20260910134244_init/`, `prisma/seed.ts`.
- `db:up` / `db:down` / `db:migrate` / `db:seed` / `db:studio` scripts in `package.json`.
- Database (local Docker, and reproducibly Supabase) populated with the mock's 9 books, 17
  chapters, 15 questions, 21 revision sessions, 11 synthesized attempts.

## Completion criteria

- [x] `prisma migrate dev` applies cleanly against an empty database.
- [x] `prisma db seed` populates all 9 books with chapters, questions, and sessions.
- [x] Data inspectable via `prisma studio`.
- [x] Re-running the seed produces identical row counts (idempotent).
- [x] `pnpm exec tsc --noEmit` and `pnpm build` still pass.
- [x] The application keeps working from the mock (nothing wired to Prisma yet).

## Risks

- Local Postgres containers commonly squat on the default `5432` port; this project's
  `docker-compose.yml` binds `55432` on the host instead to avoid collisions — override via
  `POSTGRES_PORT` if that also conflicts.
- Prisma 8 is in release-candidate status as of this phase; pinned to the latest stable
  `6.19.3` instead. Revisit the major upgrade once 8.0.0 is generally available.
- Prisma's postinstall generation scripts are blocked by pnpm's default security policy;
  `pnpm-workspace.yaml` explicitly allows builds for `prisma`, `@prisma/client`, and
  `@prisma/engines`.
- `package.json#prisma.seed` is deprecated in favor of a `prisma.config.ts` file starting in
  Prisma 7 — fine for now, revisit alongside the eventual major upgrade.
- Seed inserts are sequential (not batched) for clarity over the small mock dataset; revisit
  if seed runtime becomes a problem.
